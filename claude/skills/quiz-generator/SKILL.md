# quiz-generator スキル

問題集の写真と間違えた問題番号から、類似・関連問題のHTML問題集を生成する。

**画面・印刷用の主成果物はHTML1本**（印刷はブラウザの「印刷 → PDFに保存」）。ただし**Drive配布用にはPDFも必ず作り、HTML＋PDF＋log の3点で上げる**（下記ステップ7の「配布の関門」。Driveプレビューや他PCでは自己完結HTMLがソースの文字の羅列になり読めないため）。docxは作らない。
体裁の正典は `~/.claude/skills/quiz-generator/references/html-template.md`。
**生成前に必ずこのテンプレートを読むこと。**

**★既存の成果物は「使う・見せる・作り直す」前に現行スキルで棚卸しする（2026-08-13）**：過去の類題集・模試を再利用／再掲／作り直す前に、まず `bash references/run_checks.sh <既存HTML> <既存log.json>` を通す。**[NG]（check_pitfalls の pitfall 欠落・「▶よくある誤り」0本）や docx 成果物は現行スキル以前の旧版**＝作り直し対象。「最新スキルか確認して」は日付推測でなくこの関門で判定する。

## ステップ 0：写真の受け入れ（必須・省略禁止）

**このステップは Claude が全部やる。ユーザーは撮った写真を置くだけでよい。**
以前はここを人手でやっていた（向きを直す・ページ番号を読む・ファイル名を付ける）が、
skillの中に取り込んだ。

### 0-1　向きを決める

スマホの見開き写真は**EXIFでは向きが直らない**。撮り方でばらつくので機械任せにしない。

```bash
python <このskill>/references/prep_images.py --thumb <作業フォルダ> <写真...>
```

縮小版が出るので**必ず目で見て**1枚ずつ回転を決める。実測の目安（2026-08-08 地理）：

| EXIF補正後の形 | よくある向き | 指定 |
|---|---|---|
| 縦長（例 3000x4000） | 本を横倒しに置いて撮った | `@90`（反時計） |
| 横長（例 4000x3000） | 上下が逆さま | `@180` |

**目安であって規則ではない。** サムネイルで文字の向きを確かめてから決める。

### 0-2　分割して読める大きさにする

安全フックが1ファイル100KB超をブロックするため、そのままでは読めない。

```bash
python <このskill>/references/prep_images.py <作業フォルダ> "写真A@90" "写真B@180" ...
```

見開きを左右に割り、さらに上下に割って98KB未満に収める。
**カラーのまま扱う**（グレーにすると赤い手書きの印が印刷の線と区別できなくなる。
しかも実測ではカラーの方が小さい）。

### 0-3　ページ番号を読み取って確定する

出力を読み、**ページ隅のノンブル・単元名・教科書対応ページ**からページ番号を割り出す。
割り出したら `=p18-19` を付けて 0-2 をやり直し、正しい名前のファイルにする。

ページ番号が確定しないまま問題を作ってはならない（ページ取り違えは実際に起きている）。

### 0-4　読み取り結果を読み上げて確認を取る（エコーバック・必須）

```
写真7枚を次のとおり読みました。違っていたら教えてください。

  1枚目 → p.18-19「寒帯・亜寒帯・温帯の土地に暮らす人々」（教科書P.36〜41）
  2枚目 → p.20-21「乾燥帯・熱帯の土地・高地に暮らす人々」（教科書P.42〜47）
  ...
```

**ここで止まって返事を待つ。** 勝手に先へ進まない。

### 0-5　赤い印があれば、この確認と同時に間違い箇所まで読む（必須・2026-08-13 専務指摘）

**写真に赤い手書きの印（間違い箇所）があるなら、ページ確認を求めるその時点で、
ステップ1-B の①②（機械検出＋目視判別）まで実行し、ページ特定と間違い箇所を
まとめて提示して一度に確定を取る。**
「まず画像を確認して」と言われた時点で赤斜線の解析を後回しにしてはならない
（＝『画像の確認』と『間違い箇所の読み取り』を別ターンに割らない。
2026-08-13 に、画像アップ→確認要求の時点で赤斜線を読まず後回しにして叱責された）。

- 印がテキストで指定される（1-A）場合、または印が無い場合は、ページ確認だけでよい。
- 赤い印がある場合は、下のエコーバックに **ページ特定＋間違い箇所（＋印の無かったページ）** を
  1通にまとめて出し、**両方に対する返事をもらってから**ステップ2（設計）へ進む。

## ステップ 1：間違えた問題を特定する

受け取り方は2通り。**どちらでもよい。**

### 1-A　テキストで受け取る（例：p.13 ③(4)、p.7 ②(2)）

そのまま使う。確認は不要。

### 1-B　写真の赤い印から読み取る

**印の付け方は教科・本人によって違う。** 決めつけず、まず何の印かを見る
（地理では「空欄の丸数字を通る赤い斜線1本＝1問」だった）。

**手順は3段。機械→目視→本人確認の順で、どれも飛ばさない。**

```bash
python <このskill>/references/find_redmarks.py <ページ画像...>
```

**① 機械が候補を絞る。** 赤くて線状で紙の上にあるものを拾う。見落としを防ぐのが目的。

**② Claude が目で判別する。** 候補の座標を切り出して拡大し、手書きか印刷かを見る。
**機械の出力をそのまま信じてはならない。** 実際に、印刷の見出し・★・国旗・
地図の国境線・雨温図の折れ線・イラストがすべて候補に入った（2026-08-08 地理）。

**斜線が小問番号（丸数字）の近くにあるときは、番号の行だけを高解像度で切り出し、
『どの丸数字の上に線があるか』を1つずつ確定する。** 隣り合う番号を取り違えやすい
（2026-08-13 に、②が無傷で①③に斜線があったのを①②と誤読して訂正された）。
赤だけを白地に強調した「赤マップ」を1枚作って全体の斜線位置を俯瞰してから、
各クラスタを原寸で読むと取りこぼし・取り違えを防げる。

**③ 読み取った番号を本人に読み上げて確認を取る（エコーバック・必須）。**
番号だけでなく**問題文の書き出しを添える**。番号だけでは合っているか判断できない。

```
赤い印から、間違えた問題を次のとおり読み取りました。違っていたら教えてください。

  p.18「寒帯・亜寒帯・温帯の土地に暮らす人々」
    ④ 針葉樹林の…／⑧ 永久凍土の…／⑩ 建物を高床に…／⑬ 白夜と…／⑯ 混合農業の…
  p.20「乾燥帯・熱帯の土地・高地に暮らす人々」
    ③ オアシスの…／④ 遊牧の…／…

  印が見つからなかったページ：p.19、p.21〜24
```

**印が無かったページも必ず並べて言う。** 見落としたのか本当に無いのかを本人が判断できる。

**ここで止まって返事を待つ。**

**判読不明な問題文がある場合は作成前に確認する（事後修正しない）。**

## ステップ 2：作成前に必ず聞く3つの質問

インプットが揃ったら、問題生成の前に以下を確認する。

### Q1：1問あたりの生成数
```
1問あたり何問生成しますか？
デフォルトは「類似1問＋関連（応用）1問」です。
```

### Q2：難易度設定
```
難易度を設定してください。
オリジナルの問題を 0 として：

  -1　易しめ（覚えていることをそのまま問う＝想起だけで解ける）
   0　同等（元の問題と同じ頭の使い方・同じ key_point）
  +1　やや応用（**使う規則・解法を自分で選ばせる**／2つ以上の事項を関係づける）
  +2　発展（**初見の設定から自分で組み立てる**／なぜそうなるかを説明する）
  ※ 難易度は「手数」でも「記述の量」でもなく**2軸（①内容の複雑さ ②頭の使い方）**で上げる（2026-08-20 2軸化）。
  　 工程を増やしただけ・記述にしただけでは上がらない。

類似問題と関連問題で別々に設定できます。
デフォルト：類似＝0、関連＝+1
```

### Q3：出力ファイル名（任意）
```
ファイル名はありますか？（省略可、省略時は自動命名）
```

## ステップ 3：画像の読み取り（2段階で同時実施）

前処理と向きの決定は**ステップ0で済んでいる前提**。まだなら先にステップ0へ戻る。

- ファイル名の `a` が上半分、`b` が下半分。境界は40px重ねてあるので、境目の行は消えない
- 「※圧縮の下限」と出たものは、読んだときに判読できるか意識して確認する

### 3a：全ページの視覚強調を読み取る（JSON用）★飛ばしやすい

**渡された写真は1枚残らず読む。** 間違えた問題があるページだけではない。

**なぜ全ページなのか**：この `visual_emphasis` が **mock-test-generator の主食**になる。
模擬テストは**出題範囲全体**から作るもので、間違えた箇所はそこに重みを乗せるだけ
（コア項目の3軸のうち間違い記録は3分の1）。
解説書§4いわく「visual_emphasis が最重要。これがあれば模擬テストは写真なしで作れる」。
**ここを間引くと、範囲の一部しか出ないテストになる。**

（2026-08-08 に7枚渡されて2見開きしか読まず、範囲の3分の1しか覆わない log.json を作った）

**枚数の突き合わせ（必須）**：JSONを書く前に
**「渡された写真の枚数」と「`pages_scanned` が覆うページ数」が合っているか**を数えて確かめる。
`pages_scanned` と `visual_emphasis` の数が一致していても、
**読んだページ数そのものが足りなければ意味がない**（両方2件なら整合チェックは通ってしまう）。

以下を読み取ってJSONの`visual_emphasis`に記録する。
問題文を1問1問読む必要はない。テキスト固有の強調表現に集中する。

- 単元名・CAN-DO・基本文（太字・色付き・囲みになっているもの）
- ポイント・まとめ・チェック欄の内容
- 繰り返し登場するパターン・問題形式

### 3b：指定問題の問題文を判読する

- 間違えた問題番号のリストに対応する問題文のみ判読する
- 図・表・グラフを使う問題は「p.XX の図〇〇を参照」と記録する（図は埋め込まない）
- 不明確な箇所は**この段階で**ユーザーに確認する

## ステップ 4：類似・関連問題の設計ルール

### 類似問題（デフォルト難易度 0）
- 元の問題と同じ形式・スキルを問う
- 数値・地名・人物名・条件などを変更する
- 元の問題文をそのまま流用しない

### 関連（応用）問題（デフォルト難易度 +1）

**★全教科共通の土台：関連問題は「よくある誤り（つまずき）」を突く設計にする（2026-08-10 専務指示。英語は特に効く）。**
- 教科・構造を問わず、関連問題は**その単元で生徒がつまずく誤答を1つ以上ねらって**作る（ただ別の設問に替えるだけにしない）。
- **巻末②解説に「▶よくある誤り」を1行必ず書く（全教科）**。`log.json` の各problemに `"pitfall"` タグを付ける。
- **生成前に、その単元の「つまずきカタログ」を2階建てで用意する（数学・英語も含め全教科）**：
  - **① 構造的な誤り＝常設カタログ**（単元をまたいで繰り返す型。抜け漏れ防止のチェックリスト）：数学＝下の P1〜P10（単元別。文字と式はP系。他単元は同様に用意）、英語＝下の E1〜E12（文法基礎）、国語＝文法（品詞・活用・敬語・係り受け）、理科＝計算系（単位換算・密度・濃度・圧力・オームの法則・有効数字・グラフ読み）、社会＝型（時差計算・地図記号・縮尺・資料の誤読・因果の取り違え）。
  - **② 単元固有の誤り＝生成時に必ず足す（全教科・数学と英語も例外でない）**：その単元の教材（ワークのまとめ/ポイント・実際の設問）と必要ならwebを読み、その単元でしか出ない罠を洗い出す。例＝英語なら比較級 -er/more・good→better・不定詞 to+原形、数学なら各単元固有のミス（反比例の比例定数の符号、作図の意味の取り違え）、地理なら各気候帯の取り違え。
  - **★カタログは「最低ライン」であって「上限」ではない。** 常設カタログに無いからと単元固有の罠を見落とさない。常設＝必ず確認する土台、単元固有＝その都度の判断で上乗せ。**①と②の両方をやって初めて穴が埋まる**（①だけに固定して機械的に当てはめるのは失敗）。
  - 単元の類題集は全体で①②のつまずきをできるだけ広く覆う（穴を残さない）。
- これは**模試（mock-test-generator）でも同じ**＝コア項目に「つまずき軸」を必ず入れ、頻出の誤りを突く小問を混ぜ、解説に「よくある誤り」を書く（mock側 SKILL.md 参照）。

そのうえで、関連問題の**作り方（構造）は教科で分ける（下記）**。

**教科で作り方を分ける（2026-08-10 専務指示。数学だけ「段階上げ」方式に変更、他教科は従来どおり）。**

**▼ 数学＝「段階上げ」方式（＝類似2・類似3をつくるイメージ）**
- 関連は**別角度のメタ問題にしない**。類似と**同じ解法スキルの地続き**で、難易度を一段だけ上げた"類似2"を作る。
- 上げ方は次の3つだけ。**記述の殻（なぜ／どう違う／誤答さがし／比較）で +1 にするのは禁止**（計算問題のまま難しくする）：
  1. **数を複雑にする**（整数→分数・負数・累乗、桁・項を増やす）
  2. **手数を増やす**（1ステップ→2〜3ステップ）
  3. **同系スキルを複合する**（例：単位そろえ＋代入を1問に）
- こうして **`key_point` が類似より必ず一段上がる**ようにする。**類似と関連で key_point が同一になったら「問い方替え」＝失敗**（2026-08-10 の文字と式で全ペアが同一key_pointになり指摘を受けた）。
- **★上げ方は「2軸」で考える（2026-08-20 第2次改訂）。** 数学の難易度の**主軸は内容の複雑さ**
  （要素相互作用性＝一度に関係づける要素の数＝内在的負荷）。**上の3つ（数を複雑に・多段・複合）で
  内容そのものを難しくすれば、使う解法が一つに決まったまま（recall）でも +1 になる**
  ＝これが数学の正道（計算問題のまま本当に難しくする）。
  - ただし**外在的な手数（余計な工程＝busywork）を増やしただけは +1 にならない**。
    増やすのは**本質的な複雑さ**（項・負数・分数・かっこが同時に絡む）であって、作業の煩雑さではない。
  - さらに上げるなら**その難しい内容の上に select（どの解法・性質を使うか選ばせる）**を乗せる（従軸）。
    ★中身が簡単なまま select の形にしても簡単なまま（2026-08-20 専務指摘）。
  （記述の殻で +1 にするのが禁止なのは 2026-08-10 のとおりで変更なし。）
- さらに上げるなら同じ要領で類似3（難易度 +2）まで作れる（数の設定は難易度設定に従う）。
- **★段階上げは「負荷の増量」で終わらせない＝つまずき駆動にする（2026-08-10 専務指摘）。** 「数を増やす・分数にする」だけの機械的な増量は不可。**各 類似2・類似3 に、その学年でつまずく誤答（下のカタログ）を1つ以上ひもづけ、その誤りが自然に起きる数・形を選ぶ**。巻末②解説に **▶よくある誤り** を1行必ず書いて罠を自覚させる。**単元の類題集は全体で下のカタログをできるだけ広く覆う（穴を残さない）**。`log.json` の各problemに `"pitfall":"P4"` のようにタグを付ける。
- **中1「文字と式」つまずきカタログ**（他単元も、生成前に同様の誤答カタログを web/教科書ベースで用意してから設計する）：
  - **P1 符号と累乗の範囲**：-a² と (-a)²、-a³ の符号（2乗する範囲）
  - **P2 代入のかっこ落とし**：x=-3 で x² を -9 とする（正 (-3)²=9）
  - **P3 係数と累乗の混同**：2b² を (2b)²=4b² とする／(2a)² と 2a²
  - **P4 分配の符号**：-(7a-3)、-2(a-4)、数×( ) の後ろの項の符号を変え忘れる
  - **P5 係数1の扱い**：x=1x、4x-3x=1 と文字を消す、-y=-1y
  - **P6 異種項の誤結合**：3a+2b=5ab、x と y、a と a² を1つにまとめる
  - **P7 分数係数**：代入・約分・通分の誤り
  - **P8 ÷を分数に**：a÷(bc) の分母に入れる文字の取り違え
  - **P9 単位そろえ**：そろえず足す／m↔cm の向き（×100か÷100か）を逆にする
  - **P10 文字式の意味**：6n+3 を「6の倍数」と答える／位取り 10a+b／連続整数
- **中1「方程式」つまずきカタログ**（文字と式に続く単元。2026-08-17 追加）：
  - **P11 方程式と式の混同**：3x+2 のような**式**を方程式と答える／等式・不等式・方程式の区別
  - **P12 等式の性質の適用ミス**：両辺に同じ数をかけるつもりで片辺だけ／0でわる／-x=5 を x=-5 にできない

**▼ 数学以外（地理・歴史・理科・英語 等）＝従来どおりの構造**
- 同じテーマ・概念を別の角度から問う
- 「なぜ？」「どう違う？」など思考を要する記述を含める
- 指定語句を使った記述問題を積極的に採用する
- **ただし上の「よくある誤り」土台は必ず適用する**＝別角度に替えるだけでなく、その単元のつまずき（下のカタログ）を突く設問にし、巻末に「▶よくある誤り」を書く。**英語は特に、文法の定番ミスをねらった選択肢・並べかえ・書きかえで作ると効く**。

**■ 英語のつまずきカタログ（中1・E1〜E12。学年が上がれば足す）**
- **E1 三単現の -s**：He play → plays／I plays → play
- **E2 be動詞と一般動詞の混在**：I am play／He is have
- **E3 冠詞・名詞の複数s**：a apple→an apple／three book→books
- **E4 語順（疑問・否定の do/does、修飾の位置）**：Do you can〜／What time is it
- **E5 代名詞の格**：I / my / me / mine、his / her
- **E6 前置詞**：in / on / at（時・場所）、go to school の to
- **E7 数えられる/られない名詞**：many / much、a lot of、water に s を付けない
- **E8 時制と過去形**：go→went（不規則）、規則動詞の -ed のつづり
- **E9 be動詞の一致**：is / are / am
- **E10 スペル・大文字**：文頭・固有名詞・I、-ing / -ed のつづり
- **E11 疑問詞と答え方**：Yes/No の対応、Whose→所有で答える
- **E12 所有格の 's**：Tom's book

### 難易度ガイドライン

**難易度は「手数」でも「記述の量」でもなく、2軸（①内容の複雑さ ②頭の使い方）で決める**
（2026-08-20 改訂・2軸化）。模試側の `complexity`（low/mid/high）＋ `load`（recall/select/construct）と同じ物差し。

**主軸が教科で変わる：**
- **計算・複合が作れる教科（数学・理科計算・英語）**＝**①内容の複雑さが主**。
  下表の +1/+2 は、**内容の要素相互作用性を上げる**（項・負数・分数・かっこの複合・多段）ことで作る。
  **使う解法が一つに決まったまま（recall）でも、内容が難しくなれば +1**。
- **暗記が原子的な教科（漢字・社会用語）**＝**②頭の使い方が主**（1項目を複雑にできないため）。
  下表の +1/+2 は select／construct へ持ち上げて作る。

| レベル | 上げ方（主軸で読む） | 中身 |
|--------|---|------|
| −1 | 単純・recall | 覚えていることをそのまま。要素が少なく、使う規則が一つに決まっている |
| 0 | 元と同じ | 元問題と同じ複雑さ・同じ認知過程・同じ key_point（数値や題材だけ変える） |
| +1 | **複雑さを上げる**／または select | 要素を増やし複合する（数学）／使う規則を自分で選ばせる・関係づける（暗記系） |
| +2 | さらに複雑＋construct | 多段で複合（数学）／初見から組み立てる・なぜそうなるかを説明する（全教科） |

**★やってはいけない上げ方**：**外在的な手数（余計な工程＝busywork）を増やしただけ**／記述にしただけ／
配点や語句指定を足しただけ／中身が簡単なまま select の形にしただけ。
＝**本質的な複雑さ（内在的負荷）を上げる**か、**頭の使い方を変える**かのどちらかでないと難易度は上がらない
（2026-08-20 に模試側で「余計な手数を増やしただけ」の失敗をして叱責された）。

### 教科別の注意点
- **計算問題**（数学・理科・時差など）：数値を変えて同じ解法で解けるものを作る
- **記述問題**（社会・国語）：語句指定は毎回変える
- **選択問題**：選択肢の構成（正答の位置・ダミーの質）を意識する

## ステップ 4.2：図・表・地図・写真を使う問題の扱い（必須）

**大前提1：図・表・地図・写真を問題集に埋め込むことは禁止する（著作権上の理由）。**
新しい図を生成して代用することもしない。

**大前提2：元の問題文をそのまま流用することは禁止する。**
これは類題集の根幹であり、図を使う問題であっても例外を認めない。
ワーク原本を参照させる場合、生徒はワークを開くため、
**同じ問題文にすると本人が書き込んだ答えがそのまま目に入る。**

### 判定フロー

```
その問題は図がないと解けないか？
  ├─ NO（図は補助的） ──→ 【分類A】図に依存しない新問題を作る
  └─ YES（図が必須）
        ├─ 図の内容を文章で説明できる → 【分類B】文章化して自己完結型にする
        └─ 文章化できない　　　　　　 → 【分類C】原本参照＋問いをずらす
```

### 問題種別で分ける（類似はC不可・関連はC可／2026-08-09）
- **類似問題**：答えがワークの元問題と同じ（言い回しだけ変える）。→ **A/B必須・C禁止**。
  同じワーク図を参照させると設問も答えも元と同一になって複製化し、本人の書き込み答えも目に入るため。
- **関連（応用）問題**：答えをずらす前提。→ **C を採用可**。同じワーク図を参照させ、
  元と違う設問・違う答え（比較／理由／別対象／条件変更）にする。
  ワーク自体が図表絵の読み取りを主目的にしている単元・入試で頻出の図読みタイプなら、
  B可能でも積極的にCを選ぶ。ワークを開かせること自体はデメリット扱いしない。

### 【分類A】自己完結型に作り替える（第一選択）
図に依存しない形に問題を再設計する。通常の類似・関連問題として扱う。

### 【分類B】図の内容を文章化する
図から読み取れる情報を問題文に書き下し、図がなくても解ける形にする。
例：「右の地図中Aの地域」→「赤道付近に位置し、一年中高温多雨な地域」

### 【分類C】原本参照＋問いをずらす

図そのものを見せる必要があるが文章化できない場合に採用する。
**図は原本を見せ、問いは必ず新しく作る。**

問題文の直前に赤字（テンプレートの `.src` クラス）で注記を入れる。

```
※ワークP.◯の図／地図／写真を見て答えなさい
```

**問いのずらし方（同じ図から別の答えを引き出す）**

| ずらし方 | 例 |
|---------|---|
| 答えの対象を変える | 「Ⅰ〜Ⅳの文字名を答えよ」→「Ⅰ〜Ⅳの文明がおこった川名を答えよ」 |
| 順序・比較を問う | 「A〜Cは何教か」→「A〜Cを成立が古い順に並べよ」 |
| 一部に絞って深掘り | 「A〜Cを選べ」→「Bの宗教の開祖と聖典を答えよ」 |
| 理由・特徴を問う | 「Dはどれか」→「Dがそう判断できる理由を書け」 |

**禁止事項**
- 元の問題文と同一・ほぼ同一の設問にすること
- 元の解答と同じ答えになる設問にすること
- 同じセクションの関連問題と答えが重複すること

### どうしてもずらせない場合

図の要素が少なく、どう問うても元と同じ答えにしかならない図が稀にある。
その場合は**独断で流用せず、ユーザーに次を提示して判断を仰ぐ**。

```
【判断をお願いします】
p.◯ ◯◯の図は、どう問いを変えても元の問題と同じ答えになります。
　ア この問題は出題しない（他の問題で代替する）
　イ 元の問題のまま出題する（ワークに答えが残っている点は了承のうえ）
```

### 分類Cを使った場合の必須処理
- ログJSONの該当problemに `"figure_dependent": true` を付与する
- チャットで「原本参照にした問題」と**どうずらしたか**を一覧で報告する

### 判定の報告
ステップ3bの判読結果を提示する際、図を使う問題については
**A／B／C のどれで処理するかを明記してユーザーの確認を取る。**

## ステップ 6：問題記録 JSON の生成

HTML と同時に、作成した問題の記録を JSON ファイルとして出力する。
**mock-test-generator との連携および次回の重複回避に使う。**

### ファイル名
```
<HTMLと同じベース名>_log.json
例: 英語_Unit1-2_類似関連問題集_log.json
```

### JSON 構造

```json
{
  "created_at": "YYYY-MM-DD",
  "subject": "教科名",
  "unit": "単元名（例: Unit1-2）",
  "difficulty": { "類似": 0, "関連": 1 },
  "test_range": ["p.12-13", "p.14-15", "..."],
  "pages_scanned": ["p.12-13", "p.14-15", "..."],
  "visual_emphasis": [
    {
      "page": "p.12-13",
      "unit": "単元名",
      "can_do": "CAN-DOの内容（英語など明示されている場合）",
      "key_sentences": ["基本文1", "基本文2"],
      "emphasis_points": [
        "強調されていたポイント1",
        "強調されていたポイント2"
      ]
    }
  ],
  "problems": [
    {
      "source": "p.26 ③",
      "type": "類似",
      "difficulty": 0,
      "question_summary": "問題文の要約（30字程度）",
      "key_point": "問われているスキル・文法事項",
      "answer": "答え",
      "wrong_count": 1,
      "pitfall": "狙うつまずき（例: P4 分配の符号／B1 見た目分類）。無ければ \"なし（知識確認）\""
    }
  ]
}
```

※ `pitfall` は**関連（数学は類似2・類似3）に必須**（2026-08-11）。ステップ4の
　 つまずき駆動を機械で担保する `check_pitfalls.py` がこの欄を見る。空欄・キー無しは配布不可。

※ `visual_emphasis` は mock-test-generator が画像なしでコア項目を特定するために使う。
　 教科・出版社によって強調の形式が異なるため、テキスト固有の構造に合わせて柔軟に記録する。

※ `test_range` は**次のテストの出題範囲**（見開き単位）。`pages_scanned` は**実際に読んだページ**。
　 この2つは別物で、範囲の一部しか読んでいなければ `test_range` のほうが多くなる。
　 範囲から外すと決めたページは `visual_emphasis` の側に `"out_of_range": true` を付ける。

※ **ページの呼び名は1通りに統一する**（2026-08-19）。`test_range`・`pages_scanned`・
　 `visual_emphasis[].page` の3か所は**同じ文字列**で書く（例：すべて `"P.3 見開き"`）。
　 片方に `"P.3(見開き：人類の出現と古代文明)"` のような説明を付けると、機械は別ページとみなす。
　 説明を残したいときは `visual_emphasis[].unit` に書く（`page` には入れない）。
　 **`test_range` は必ず書く**（無いと検査が「範囲が分かりません」で止まる）。
　 ※ check_coverage.py 側でも `P.3` 部分だけを取り出して比べるようにしてあるが（2026-08-19）、
　 　 出す側で揃えるのが本筋。

### 書いたら必ず通す（省略禁止）

```bash
python ~/.claude/skills/quiz-generator/references/check_coverage.py <log.json>
```

`test_range` の各ページが `pages_scanned` と `visual_emphasis` の両方に載っているかを1ページずつ照合する。
**`[NG]` が出たら、不足ページの写真を求めてJSONを作り直す。** そのまま模試に渡してはならない。
`pages_scanned` と `visual_emphasis` の件数が一致していても、読んだページ数自体が足りなければ
このチェックでしか見つからない（2026-08-08 に7枚渡されて2見開きしか読まなかった件）。

### wrong_count の設計思想

- **JSONにエントリが存在すること自体が「間違えた」の証拠**
- 指定された問題のみJSONに記録される（全問判読はしない）
- 指定されなかった問題のエントリは存在しない

### wrong_count の更新ルール

- 初回生成時は `wrong_count: 1`（生成＝1回間違えた事実）
- ユーザーが「また間違えた」「別バージョンを作って」と言った場合、
  対象問題の `wrong_count` を +1 してJSONを上書き保存する

| wrong_count | mock-test-generator での扱い |
|-------------|---------------------------|
| 1 | 重要項目として必ず含める |
| 2以上 | 必出項目として必ず1問以上含める |
| エントリなし | ①②の2軸のみで判断 |

### 生成方法

HTML 生成スクリプトの末尾に以下を追加する：

```python
import json
log = {
    "created_at": today,          # YYYY-MM-DD
    "subject": "教科名",
    "unit": "単元名",
    "difficulty": {"類似": 0, "関連": 1},
    "problems": [
        # 各問題のオブジェクトを配列で列挙（wrong_count: 1 で開始）
    ],
}
with open(log_path, "w", encoding="utf-8") as f:
    json.dump(log, f, ensure_ascii=False, indent=2)
```

**`ensure_ascii=False` を必ず付ける**（日本語がそのまま読める形で保存するため）。

## ステップ 7.5：answer-validator からの修正依頼への対応

### トリガー
- 「answer-validator 検証結果」を含むテキストが渡された場合
- 「✗の問題を修正して」「検証結果に基づいて修正して」などの言及がある場合

### 処理手順

**① 修正内容の確認**
渡された検証結果から ✗ の問題を全件抽出し、以下を確認する。

| 確認項目 | 内容 |
|---------|------|
| 問題番号 | どの問題が対象か |
| 修正種別 | 解き直し不一致 / 転記ミス のどちらか |
| 修正案 | answer-validator が提示した修正内容 |

**② 修正の適用**

- **解き直し不一致（答えが間違い）**：問題文・答え・解説を修正案に基づいて修正する
- **転記ミス（巻末①②の不一致）**：巻末①を正として巻末②を修正する

**③ HTML の再生成**

修正を適用してHTMLを再生成し、同じ場所に上書き保存する。
ファイル名は元のファイル名を維持する（`_fixed` などのサフィックスは付けない）。
**Driveへコピー済みの場合は、配布の関門スクリプト（publish_to_drive.sh）を再度通して上書きする**（PDFも作り直し、古い版・古いPDFが残らないようにする）。

**④ 再検証の案内**

```
修正済みHTMLを出力しました。
answer-validator で再検証することを推奨します。
```

## ステップ 8：レベルアップ版の生成（JSON 再投入）

過去に生成した log.json を渡して難易度を上げて作り直す場合のフロー。
画像の再アップロードは不要。

### トリガー
- 「log.jsonを使ってレベルを上げて」
- 「難易度を上げて作り直して」
- 「もっと難しいバージョンを作って」

### 質問フェーズ（必須・省略禁止）

JSON を受け取ったら、問題生成の前に以下を必ず聞く。

**Q1：対象タイプ**
```
類似問題・関連問題のどちらを作成しますか？
  1. 類似のみ
  2. 関連のみ
  3. 両方
```

**Q2：難易度**
```
難易度をいくつにしますか？

  -1　易しめ（覚えていることをそのまま問う＝想起だけで解ける）
   0　同等（元の問題と同じ頭の使い方・同じ key_point）
  +1　やや応用（**使う規則・解法を自分で選ばせる**／2つ以上の事項を関係づける）
  +2　発展（**初見の設定から自分で組み立てる**／なぜそうなるかを説明する）
  ※ 難易度は「手数」でも「記述の量」でもなく**2軸（①内容の複雑さ ②頭の使い方）**で上げる（2026-08-20 2軸化）。
  　 工程を増やしただけ・記述にしただけでは上がらない。

現在の難易度：類似 = X、関連 = X（JSONの値を表示する）
```

両方の回答を受け取ってから生成に進む。

### 処理手順

**① JSON の読み取り**
- `subject` / `unit` / `visual_emphasis` / `problems[].key_point` を参照する
- 各問題の現在の `difficulty` を確認し、Q2 の回答と一緒に表示する

**② 問題の生成ルール**
- `key_point` は変えない（同じスキルを問う）
- 問題の形式・解答形式は前回と同じパターンを維持する
- 数値・語句・条件を変えて、指定難易度に合わせた内容にする
- 前回の `answer` と同じ答えになる問題は作らない

**③ JSON の更新**
- 対象問題の `difficulty` を指定された値に上書きする
- `wrong_count` を +1 する
- `created_at` を今日の日付に更新する
- ファイル名は `<ベース名>_lv<難易度>_log.json` で新規保存する
