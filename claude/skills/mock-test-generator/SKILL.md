# mock-test-generator スキル

問題集の画像と教科情報から、単元全体の模擬テスト（既定100点・50分・本番形式）を生成する。
quiz-generatorのJSONに`visual_emphasis`が含まれている場合は**画像なしで動作可能**。

**画面・印刷用の主成果物はHTML1本**（印刷はブラウザの「印刷 → PDFに保存」）。ただし**Drive配布用にはPDFも必ず作り、HTML＋PDF＋出題履歴JSON の3点で上げる**（ステップ9の「配布の関門」。Driveプレビューや他PCでは自己完結HTMLが文字の羅列になり読めないため）。docxは作らない。
体裁の正典は `~/.claude/skills/quiz-generator/references/html-template.md`（quiz-generator と共通）。
**生成前に必ずこのテンプレートを読むこと。**

## ★既存の成果物は「使う・見せる・作り直す」前に現行スキルで棚卸しする（2026-08-13）

過去に作った模試・類題集を再利用／再掲／作り直すよう頼まれたら、**中身に触れる前に、その成果物が現行スキルで作られているかを機械で確かめる**：

```bash
bash ~/.claude/skills/quiz-generator/references/run_checks.sh <既存HTML> <既存の出題履歴/log.json>
```

- **[NG]（特に check_pitfalls の pitfall 欠落・「▶よくある誤り」0本）が出たら現行スキル以前の版**＝つまずき駆動が入っていない → **作り直す**。
- **docx の成果物は旧版**（HTML＋PDF＋3点配布・つまずき駆動より前）＝原則すべて作り直し対象。
- 「最新スキルで作られているか確認して」と聞かれたら、日付の推測ではなく**この関門を実際に通して**判定する（2026-08-13 に中間の地理模試が旧版のまま残っていた＝pitfall 0・▶ 0本で判明）。

### 難易度ゲートだけで弾かれた既存テストの回復（Step3〜5をやり直さない・2026-08-19）

棚卸しの `run_checks.sh` が **`check_difficulty.py` だけで [NG]**（＝leak・pitfall・配点・承認は通り、
`load` 未設定・旧ラベル・または応用の構成比のみ失敗）だったときは、**新規生成に戻らない**。
設定（満点・時間・記述量・難易度・配合）とコア項目・構成は**既存の承認が生きている**ので、
**ステップ3の質問・ステップ4/5の承認ターンはやり直さず**、次の難易度回復だけを行う：

1. 既存の出題履歴JSONと巻末を材料に、**各設問へ load と complexity を正直に付ける**
   （`load`＝recall/select/construct／`complexity`＝low/mid/high。トップに `difficulty_primary`）。
2. **教科の主軸で回復の仕方が変わる**（下記「難易度は2軸」）：
   - **計算・複合が作れる教科（数学・理科計算・英語／difficulty_primary=complexity）**
     ＝**内容そのものを難しくする**（項数・負×分数×かっこの複合・多段）。応用基準＝
     単純(low)≤30%・高複雑(high)≥30%・中+高≥70%。**recall のままでよい**。
   - **暗記が原子的な教科（漢字・社会用語／difficulty_primary=process）**＝
     recall の問いを select／construct へ差し替える。応用基準＝recall≤30%・construct≥15%・s+c≥70%。
   いずれも**配点移動・ラベル貼り替え・記述の本数増やし・外在的な工程（手数）増やしはしない**
   （★余計な手数を増やしても難易度は上がらない。本質的な複雑さを上げる＝2026-08-20 の教訓）。
3. **差し替え案（どの問を、どう変えるか）は必ず表で提示して承認を得てから着手する。**
   出題の中身が変わる以上、承認はステップ4・5と同じく必要（2026-08-20 専務叱責）。
   このとき**差し替え後の構成比（主軸の内訳と%）も併せて示す**
   ＝ステップ5.6の承認ターン③と同じ内容（2026-08-20 新設）。
4. HTML＋出題履歴JSONを作り直し、`run_checks.sh` を **[OK]** になるまで回す。
5. 中身が変わったので **answer-validator を通し直す**（av_begin→check_leak→av_report→av_stamp。
   HTMLの sha が変わる＝スタンプ再発行必須）。
6. **Driveは上書きになるので、配信の可否を確認してから** `DESIGN_BRIEF` 付きで
   `publish_to_drive.sh` で配信する。
※ 既存JSONの `approvals` ブロックはそのまま引き継ぐ（設定・承認を専務が変えていないため）。
　 pitfall や他の関門も同時に [NG] のときは旧版扱い＝**通常の作り直し**（ステップ1から）に戻す。

## ステップ 1：インプット収集

| 必要なもの | 形式 | 必須 |
|-----------|------|------|
| quiz-generator の JSON ログ | JSONファイル | △（あれば） |
| 問題集のページ写真 | 画像（複数可） | △（JSONにvisual_emphasisがなければ必要） |
| 教科名 | テキスト | ○ |
| 出題範囲 | テキスト（ページ指定 or 全ページ） | ○ |
| 前回の出題履歴 JSON | JSONファイル | △（2回目以降はあれば） |

### インプット受け取り時の確認フロー

```
① JSONを受け取る
      ↓
② JSON に visual_emphasis があるか確認する
   ある → 「画像は不要です。このまま進めます。」と伝える
   ない → 「画像をアップロードしてください。」と促す
      ↓
③ JSONがない場合は「JSONログはありますか？」と確認する
   ある → アップロードを促す
   ない → 画像のアップロードを促してそのまま進む
      ↓
④ 「前回の出題履歴JSONはありますか？」と確認する
   ある → アップロードを促す
   ない → 初回として進む
```

## ステップ 2：コア項目の特定

コア項目は **「何を出すか」と「どう出すか」の2階建て**で決める（2026-08-17 専務指摘で①〜④に⑤を追加）。

| 階 | 軸 | 役割 |
|---|---|---|
| **何を出すか** | **① 視覚的強調**（ワークの log.json） | 範囲のどこが重いかをワーク側から取る |
| | **② 教科知識** | ワークに強調が無くても外せない項目を足す |
| | **③ 間違い記録**（log.json の wrong_count） | 本人が実際に落とした箇所を必出にする |
| **どう出すか** | **④ つまずき（一般的な落とし穴）** | 全項目に重ねて、罠を突く形にする |
| | **⑤ 設計ブリーフ（本番の変換ルール・規模）** | 前回本番の癖に合わせて出題の形と問題数を決める |

**③④⑤の3つは既定ではすべて模試に載せる**（どれか1つに寄せない）。
ただし**この配合は固定ではなく、ステップ3で変えられる**（＝同じ範囲から性格の違う模試を何本も作れる。
2026-08-17 専務指摘）。既定は「バランス」＝③④⑤を均等に混ぜる。

承認ターン①の表には**「由来」の列**を必ず付け、各コア項目が③④⑤のどれから来たかを示す。
表の下に**由来の内訳（③○件・④○件・⑤○件）**を1行添え、
**指定された配合どおりになっているか**を専務が目で見て判断できるようにする。

### ① 視覚的強調（JSONまたは画像から取得）

以下の優先順位で視覚強調情報を取得する。

| 状況 | 取得方法 |
|------|---------|
| JSONに`visual_emphasis`がある | JSONの`emphasis_points`・`key_sentences`・`can_do`を読む（画像不要） |
| JSONにないが画像がある | 画像から直接読み取る（教科・出版社固有の強調表現に注目） |
| 両方ある | JSONを優先し、画像で補完する |

### ★最初にやること：カバレッジ検査（省略禁止・目視で代用しない）

**模擬テストは出題範囲全体から作る。間違い記録は5軸のうちの1つにすぎない。**
その大前提は「渡されたJSONが範囲全体を覆っていること」なので、**何よりも先に機械で確かめる。**

```bash
python ~/.claude/skills/quiz-generator/references/check_coverage.py <log.json>
# 範囲がJSONに書かれていないときだけ
python ~/.claude/skills/quiz-generator/references/check_coverage.py <log.json> --range p.18-19,p.20-21
```

| 結果 | やること |
|------|---------|
| `[NG]` | **そこで止める。** 不足ページを画面に出して写真を求め、quiz-generator でJSONを作り直す |
| `[要確認]` | 挙げられたページの写真を開き直し、読み落としが無いか確かめてから進む |
| `[OK]` | 次へ進む |

**このコマンドを実行せずにステップ2の先へ進んではならない。**
自分の目で数えて足りていると判断するのも不可（数が揃っていると通ってしまうため。
2026-08-08 に、7枚の範囲に対して2見開き分しか入っていないJSONで模試を作りかけた）。
配点の `assert`・`check_leak.py` と並ぶ、3つ目の機械の関門である。

**【必須手順】JSONに`visual_emphasis`がある場合：**
1. 全ページの`emphasis_points`と`key_sentences`を**ページ順に全件列挙**する
2. 列挙した全項目をコア項目の候補としてリストアップする
3. ②③の軸と照合して重み付けする
4. **①で列挙した項目がコア項目リストに漏れなく反映されているか最終確認する**
   （②の教科知識だけで構成してはならない）

※ この手順を省略してコア項目リストを出力してはならない。

**画像から読み取る場合：**

**読む前に必ず前処理する（省略禁止）。** スマホ写真はそのままでは読めない
（安全フックが1ファイル100KB超をブロックする）。しかも**向きがEXIFでは直らない**。

```bash
# ① 向きを確認する
python ~/.claude/skills/quiz-generator/references/prep_images.py --thumb <作業フォルダ> <写真...>
# ② 回転とページ番号を指定して分割・圧縮する
python ~/.claude/skills/quiz-generator/references/prep_images.py <作業フォルダ> "写真@90=p18-19" ...
```

**手順は quiz-generator のステップ0（0-1〜0-4）と同じ。**
向きを目で決める・ページ番号を読み取ってリネームする・読み取り結果を読み上げて確認を取る、
の3点を飛ばさないこと。

前処理後、教科・出版社によってレイアウトが異なるため、ルールを固定せず
「このテキストでは何が重要事項として強調されているか」を判断する。
囲み・太字・色付き・繰り返しパターン・まとめ欄・ポイント欄など
テキスト固有の強調表現に注目する。

### ② Claudeの教科知識による重要度判断
テキストの強調に依存せず、その単元・内容について
「一般的に重要とされる概念・スキル」をClaudeが独自に判断する。
テキストに強調がなくても、教科の一般論として外せない項目は必ず含める。

### ③ JSONログの間違い記録
quiz-generatorが出力したJSONが渡された場合：
- **JSONにエントリが存在すること自体が「間違えた」の証拠**
- `key_point` を読み込みコア項目と照合する
- `wrong_count` が 2以上 → **必出**（必ず1問以上含める）
- `wrong_count` が 1　　→ **重要**（重要項目として含める）
- エントリが存在しない項目 → ①②の2軸のみで判断

JSONがない場合はこの軸はスキップする。

### ④ つまずき（よくある誤り）を必ず織り込む（全教科・2026-08-10 専務指示）
**本番のテストは「定番の誤り」を突いてくる。模試も同じ発想で作る。**
- コア項目ごとに、その単元で生徒がつまずく**定番の誤り**を1つ以上ひもづけ、**それを突く小問**（ひっかけの選択肢・並べかえ・書きかえ・符号や単位の罠）を必ず混ぜる。
- **巻末の解説に「▶よくある誤り」を1行書く**（なぜ間違えるか・正しい考え方）。
- つまずきは**2階建て**で考える（quiz-generator SKILL.md ステップ4と同じ）：
  - **① 常設カタログ（構造的な型・最低ライン）**＝数学 P1〜P10／英語 E1〜E12／国語=文法／理科=計算系／社会=型（時差・地図記号ほか）。抜け漏れ防止のチェックリストとして必ず確認する。
  - **② 単元固有の誤り＝範囲の教材から生成時に必ず足す（全教科・数学英語も例外でない）**。①だけに固定せず、この範囲でしか出ない罠を洗い出して突く。
  - **★カタログは「最低ライン」であって「上限」ではない**（①に無いからと単元固有の罠を見落とさない）。
- **英語は特に効く**：三単現の-s・be動詞と一般動詞の混在・語順・冠詞/複数s・前置詞・時制などの定番ミスを、選択肢や書きかえで必ず1問以上突く。

### ⑤ 設計ブリーフ＝前回本番の「変換ルール」と「規模」を当てはめる（2026-08-17 専務指摘で新設）

教科ごとの設計ブリーフ（例 `holiday/期末模試_設計ブリーフ/{教科}.md`）がある場合、**必ず先に開いて反映する**。

**★ブリーフの意味を取り違えないこと。**
ブリーフは「**前回本番で落とした問題を今回に持ち込むためのもの**」では**ない**
（2026-08-17 に理科でこの取り違えをして専務に叱責された）。
落とした箇所は上の**③間違い記録**が担当する。ブリーフが担うのは次の2つだけ：

| ブリーフが持つもの | 中身 |
|---|---|
| **変換ルール（癖）** | 出題者が**ワークのこの形 → 本番のこの形**へどう化けさせたか |
| **規模** | 本番の**大問数・小問数・記述の本数・完答（すべて選べ）の箇所数** |

#### ★ブリーフがある教科では、前回本番の画像を読み直さない（2026-08-18 専務叱責）

**ブリーフは「本番を読んだ結果」そのもの**である。作る前に本番画像へ戻るのは同じ作業の二度手間で、
トークンの無駄になる（2026-08-18 の国語で実際にやって叱責された）。

- **原則＝ブリーフを読んだら本番画像は開かない。** 判断材料はブリーフに書いてあるものが全て。
- **ブリーフに無い事実が要るとき**（配点・試験時間・大問数など）は、**画像を開くのではなく
  専務に「ブリーフに書かれていないので確認したい」と聞く**。
- 画像に戻ってよいのは**専務が「ブリーフを直せ」と言ったときだけ**。
  そのときは読み取った事実を**必ずブリーフに書き戻す**（次回また読み直す羽目にならないように）。
- ブリーフの記述が実物と食い違っていると分かったら、**その場でブリーフを直す**（放置しない）。

#### ブリーフの作り方（無い教科は模試の前にこの手順で作る）

1. **ワーク側の実体を取る**＝前回範囲の quiz log.json の `visual_emphasis`
   （＝そのときワークを読み取った内容。**ワーク画像を撮り直す必要はない**）
2. **本番側の実体を取る**＝前回本番の実物画像を読み、大問ごとに設問の形式を書き出す
3. **1と2を突き合わせ、変換ルールを抽出**する。
   「ワークで箇条書きだった知識が、本番では図の記号で問われた」のように、
   **ワークの形 → 本番の形**の対応で書く（R1・R2…と番号を振る）
4. **規模を数える**＝大問数／小問数／記述の本数／完答の箇所数／並べ替えの有無／作図の有無
5. **今回範囲のワーク（log.json の visual_emphasis）に3を当てはめ、出題像を予測**する。
   「この見開きのこの項目は、この癖でこう出る」を表にする
6. ブリーフの構成＝**A 変換ルール／B 今回範囲への当てはめ（予測）／C 反映チェックリスト／D 狙うつまずき**

#### 模試への反映

- **形**＝Bの予測像に沿って大問を組む（Cのチェックリストを1つずつ潰す）
- **規模**＝**本番の大問数・小問数に合わせる**。本番が大問7・小問31なら、模試も同程度にする
  （満点・時間が同じでも、大問5・小問18では本番の密度と違うものになる。ステップ5で照合する）
- 出題履歴JSONに `design_brief_required` と `design_brief_sha256` を入れる（ステップ8）

## ステップ 3：作成前に確認する項目

コア項目特定後、問題生成前に1回だけ質問する。

```
① 学年・クラス名を教えてください。（テスト用紙の見出しに使います。省略可）

② 満点と試験時間はどうしますか？
   既定は「100点・50分」です。
   範囲が狭い単元では小さくしてかまいません（例：国語の文法3見開き → 60点・30分）。

③ 記述問題の量はどうしますか？
   ・多め　（思考力・表現力重視）
   ・標準　（バランス型）
   ・少なめ（知識・技能確認重視）

④ 【JSONにdifficultyフィールドがある場合のみ表示】
   テストの難易度レベルはどうしますか？
   ★難易度は「問いの質」の軸で、記述の本数は③（記述量）で別に決める。
   　難易度を上げる＝記述を増やす、ではない（2026-08-19 専務指摘）。
   　★手数（工程の多さ）でもない（2026-08-20 専務指摘）。
   ・基礎　（覚えた知識をそのまま問う。知識の定着確認）
   ・標準　（知識を問いつつ、どれを使うか判断させる問いも混ぜる。理解度の総合確認）
   ・応用　（**内容そのものを難しくする（要素相互作用性を上げる）＝主軸。
   　　　　　加えて、思い出せば出る問い（recall）を減らし判断（select）・構成/説明（construct）を混ぜる**。
   　　　　　**記述の本数も工程（手数）の数も増やさない**）

   ★難易度の主軸は教科で変わる（2026-08-20 第2次改訂・下記「難易度は2軸」参照）。
   　計算・複合が作れる教科（数学・理科計算・英語）＝**内容の複雑さが主**（difficulty_primary="complexity"）。
   　暗記が原子的な教科（漢字・社会用語・国語文法）＝**思考の種類が主**（difficulty_primary="process"）。

⑤ 【設計ブリーフがある教科のみ表示】どの型の模試にしますか？（③④⑤の配合）
   ・バランス　（既定。弱点・落とし穴・本番の癖を均等に混ぜる）
   ・本番そっくり（⑤重視。ブリーフの変換ルールと規模の再現を最優先。予測の答え合わせ用）
   ・弱点つぶし（③重視。間違い記録のある項目を必出にし、周辺を厚くする）
   ・ひっかけ特訓（④重視。落とし穴を突く問題の比率を上げる）
```

### 満点・試験時間の扱い（必須）

②の回答を **`TOTAL_POINTS` / `TIME_LIMIT`** として保持し、以降のすべての工程で使う。
**この2つを固定値として扱ってはならない**（ステップ5.5の検算もこの変数で行う）。

- 回答が無ければ既定の 100点・50分 を使う
- 一度決めたら、構成案・検算・見出し・出題履歴JSONで**同じ値を使い回す**

### 配合（⑤の回答）の反映ルール

回答を **`MIX`** として保持し、承認ターン①の「由来」の内訳がこの配合になっているか確認する。

| MIX | ③間違い記録 | ④落とし穴 | ⑤ブリーフ | 使いどころ |
|---|---|---|---|---|
| バランス（既定） | ○ | ○ | ○ | 1本目 |
| 本番そっくり | △ | ○ | **◎** | 本番直前・予測の答え合わせ |
| 弱点つぶし | **◎** | ○ | △ | 間違いが多い単元の立て直し |
| ひっかけ特訓 | ○ | **◎** | △ | 知識はあるのにミスで落とすとき |

**同じ範囲でも MIX・難易度・記述量を変えれば別の模試になる。**
2本目以降は**前回の出題履歴JSONを必ず渡してもらい**、同じ項目でも切り口・形式を変える
（ステップ4の差分付記ルール＝前回と全く同じ形式で出してはならない）。

### difficultyの反映ルール

| 選択 | difficulty=0の項目 | difficulty=1の項目 |
|------|-------------------|-------------------|
| 基礎 | 全て出題対象 | 1〜2問のみ（補足として） |
| 標準 | バランスよく混在 | バランスよく混在 |
| 応用 | 1〜2問のみ（導入として） | 全て出題対象 |

**★難易度は「形式」でも「記述の量」でもなく、「中身」で上げる**
（2026-08-19／2026-08-20 専務指摘・全教科共通）。**「応用＝記述中心」も「応用＝工程が多い」も誤り。**
記述とそれ以外の比率は③（記述量）で決めたとおりに保つ。

#### 難易度は2軸（認知負荷理論／Bloom・SOLO が共通して指すもの・2026-08-20 第2次改訂）

| 軸 | 中身 | 上げ方 |
|---|---|---|
| **① 内容の複雑さ（主軸）** | 一度に頭の中で関係づける**要素の数**＝要素相互作用性（内在的負荷） | 計算の項数・**負×分数×かっこの複合**・多段・複数事実の関係づけで上げる。**手順が一つ(recall)でも難しくなる** |
| **② 思考の種類（従軸）** | ①の「関係づけ・構成」の側面を名づけたもの＝recall/select/construct | recall を減らし select（判断・関係づけ）・construct（説明・産出）を混ぜる |

**主軸が教科で変わる：**
- **計算・複合が作れる教科（数学・理科計算・英語）**＝**①内容の複雑さが主**。
  「普通の計算問題を本当に難しくする」のが正道。**recall のままでよい**（難しい計算は recall）。
  ★中身が簡単なまま select/construct のラベルだけ貼っても簡単なまま（2026-08-20 専務指摘）。
- **暗記が原子的な教科（漢字・社会用語・国語文法）**＝**②思考の種類が主**。
  1項目を複雑にできない（漢字は書けるか否か）ので、**複数を関係づける・説明させる**で上げる。

②の3区分：**規則を自分で選ぶ(select)**／**2つ以上を関係づける(select)**／
**初見の文脈へ移す・なぜそうなるかを説明する(construct)**（Bloom改訂版・SOLO・転移の距離）。

**やってはいけない上げ方**：**外在的負荷（余計な手間＝busywork）を増やす**
（「2文に共通して入る1語」など。手数が増えてもやることが想起なら難易度は上がらない＝2026-08-20 の失敗）／
配点を後半へ移す／記述を増やす／ラベルだけ貼り替える。
★**内在的負荷（本当の複雑さ）を上げるのは正当**——「手数を増やすな」は“余計な手数”の禁止であって、
本質的な複雑さを上げることまで禁じてはいない（2026-08-20 第2次改訂でこの混同を正した）。

記述を増やしたいときは③（記述量）で「多め」を選ぶ。難易度とは別の軸として扱う。

※ JSONにdifficultyフィールドがない場合は③を表示せず、標準として扱う。

## ステップ 5.5：配点の機械検算（必須・省略禁止）

**過去に「宣言100点／実際92点」「宣言15点／実際13点」の配点バグが複数回発生している。**
小問を設計したら、HTML生成前にPythonで必ず検算する。

**満点はステップ3で決めた `TOTAL_POINTS` で検算する。100を直接書かない。**
（100固定にすると、60点のテストを作るときに検算そのものが素通りしてしまう）

```python
# ステップ3で決めた値をそのまま入れる（既定は100点・50分）
TOTAL_POINTS = 100
TIME_LIMIT = 50

# 大問ごとの「宣言配点」と「小問配点の内訳」を突合する
daimon_declared = {1: 20, 2: 25, 3: 20, 4: 15, 5: 20}
detail = {
    1: [8, 2, 2, 4, 4],   # 【1】〜【5】の配点
    2: [8, 6, 4, 2, 5],
    # ...全大問分
}
daimon_time = {1: 10, 2: 12, 3: 10, 4: 8, 5: 10}   # 目安時間

total = 0
for d, items in detail.items():
    s = sum(items); total += s
    print(f"大問{d}: 実際{s}点 / 宣言{daimon_declared[d]}点",
          "OK" if s == daimon_declared[d] else "NG")
print("合計:", total, "/", TOTAL_POINTS)
assert total == TOTAL_POINTS, f"合計が{total}点です。{TOTAL_POINTS}点に修正すること"

t = sum(daimon_time.values())
assert t == TIME_LIMIT, f"目安時間の合計が{t}分です。{TIME_LIMIT}分に修正すること"
```

- 「各1点」「各2点」の設問は、**空欄・小問の個数を数えて**内訳に反映する
- 目安時間の合計が `TIME_LIMIT` になることも同時に確認する
- NGが出た場合は**問題を追加または配点を振り直し**、`TOTAL_POINTS` になるまで繰り返す

|------|------|------|
| **A** 自己完結型 | 図がなくても解ける | 図に依存しない形で出題する（第一選択） |
| **B** 文章化 | 図が必須だが、内容を文章で説明できる | 図の情報を問題文に書き下して出題する |
| **C** 原本参照 | 文章化できない | 原本を参照させ、**問いは必ずずらす** |

**基本はA→B→Cの順に「上から使えるか」を試す。**
図の情報がA（作り替え）かB（文章化）で無理なく落ち、かつ下記②に当たらないなら A・B でよい
（文章化の例：四大文明の文字→「川：（　）文字：（　）」、三大宗教の発祥地→「① インド　② パレスチナ」）。

**ただし、次の②のどれかに当たる単元・節では、B可能でも C を積極採用する**
（＝実物の図表絵を見て答える問題を入れる）。**ワークを開かせること自体はデメリット扱いしない**
——図表絵の読み取りそのものを測る目的が勝るため（2026-08-09 専務指示）。

**② Cを積極採用する条件（どれか1つでも該当）**
1. ワーク自体が図表絵の読み取り能力を主目的にしている（雨温図・資料の活用・思考力・地形図など。
   判定＝log.json の `can_do`／`key_sentences` に「読み取ろう」「資料の活用」「思考力」等、
   `visual_emphasis` に『読取のミカタ』が多い）
2. 入試・定期でその図読みタイプが頻出（トレンド。web で軽く裏取り）
3. 文章化すると答えが割れる／ヒントになりすぎる（B が破綻する）

②に当たる模試では、**図読みのC大問（またはC小問）を最低1つ入れる**ことを目安にする。
**Cの答えは、ワークの元の空欄（生徒が書き込んだ答え）と同じにならないよう必ずずらす**
（並べ替え・比較・数値差・理由など、分類の空欄以外を問う）。

**分類Cを使う場合**
問題文の直前に赤字（`color: 'C00000'`）で注記を入れ、
**元の問題と同じ設問・同じ答えにならないよう問いをずらす。**

```
※ワークP.◯の図／地図／写真を見て答えなさい
```

ずらし方は quiz-generator の同項目と同じ（答えの対象を変える／順序・比較を問う／
一部に絞って深掘りする／理由・特徴を問う）。
分類Cを使った問題は出題履歴JSONに `"figure_dependent": true` を付与し、
チャットでも一覧で報告する。

### 体裁ルール（必須）

**レイアウト目的の表組み（`<table>`）を使ってはならない。**
氏名欄・得点欄・解答欄はテンプレートの `.namebar` / `.ans` を使う。

| 用途 | 使うもの | 禁止 |
|------|---------|------|
| 氏名・日付・得点欄 | `.namebar` | `<table>` |
| 大問の見出し | `h2`（下に紺の罫線） | 背景ベタ塗り |
| 解答欄 | `.ans` の中に `<i>` を必要な数だけ | `<table>` / `<br>` の連打 |
| 原本参照の注記 | `.src`（赤字） | 図の埋め込み |
| 大問の区切り | `<section>`（印刷時に途中で切れない） | 手動の改ページ調整 |

問題文は写真から起こしたテキストなので、**必ず `html.escape()` してから埋め込む。**

### 生成後の検査（必須・省略禁止）

**① 機械の関門を通す（模試は「材料」と「出力」で2回に分ける・2026-08-11）。**

模試は材料（quiz の log.json）と出力（出題履歴JSON）で見る対象が違うので、関門を分けて通す：

```bash
# ②全範囲：生成前に、材料の quiz log.json（visual_emphasis入り）へカバレッジを通す
python ~/.claude/skills/quiz-generator/references/check_coverage.py <quiz_log.json>

# ①漏れ ④つまずき：生成後に、出力HTML＋出題履歴JSON へランナーを通す
bash ~/.claude/skills/quiz-generator/references/run_checks.sh <出力HTML> <出題履歴JSON>
```

- `run_checks.sh` は中で `check_coverage.py`（出題履歴JSONは自動スキップ）→ `check_leak.py`
  → **`check_pitfalls.py`** → 配点検算 → 承認検査 → **`check_difficulty.py`** を順に実行し、
  失敗した時点で止まる（＝ハード関門）。
- `check_pitfalls.py` は出題履歴JSONの**各コア項目に `pitfall` があるか**、巻末に
  「▶よくある誤り」が**罠の数だけ**あるかを見る。**pitfall欠落は配布不可**（罠が無い問は
  `"なし（知識確認）"` と明示。キーごと省くのは不可）。
- **`check_difficulty.py`（難易度構成ゲート・2026-08-19 新設／2026-08-20 全面改訂／2026-08-20 2軸化）** は
  難易度を**2軸**で見る（下記「難易度は2軸」）。トップの `difficulty_primary` で主軸を切り替える：
    - **`difficulty_primary="complexity"`（計算・複合が作れる教科＝数学・理科計算・英語）**＝
      主軸＝**内容の複雑さ**。**各設問に `complexity`（low/mid/high）が必須**。応用＝
      **単純(low)≤30% かつ 高複雑(high)≥30% かつ 中+高≥70%**、標準＝low≤55%・high≥1問。
      **recall 上限は課さない**（難しい計算は recall のまま応用）。
    - **`difficulty_primary="process"`（暗記が原子的な教科＝漢字・社会用語・国語文法）**＝
      主軸＝**思考の種類**。応用＝**recall≤30% かつ construct≥15% かつ select+construct≥70%**、
      標準＝recall≤55%・construct≥1問。
    - **宣言が無ければ process（従来挙動）＋[注意]。level が無いと配布不可。**
  **各設問に `load`（recall/select/construct）は常に必須**、complexity 教科は `complexity` も必須。
  **★どちらの軸も「手数」では測らない**（2026-08-20 に手数基準をやめた。手数＝作業の煩雑さは
  **外在的負荷**で、増やしても難易度は上がらない。ただし**内在的負荷＝本当の複雑さを上げるのは正当**）。
  load の判定は**その問いに答えるとき頭の中で何が起きるか**：
    - `recall` … 使う規則・知識が**一つに決まっていて、思い出せば答えが出る**。**何手かかっても recall**。
    - `select` … **複数の既習事項が競合し、どれを使うか自分で判断する**／2つ以上を関係づける。
    - `construct` … **初見の文脈・条件から自分で組み立てる**／**なぜそうなるかを説明する**。
  complexity の判定は**一度に関係づける要素の数**（low＝1手・要素少／mid／high＝複合・多段）。
  **難易度を上げる＝主軸で上げる**（複雑さ主なら計算そのものを難しく／思考主なら recall を差し替え）。
  配点移動・ラベル貼り替え・記述増やし・**外在的な工程増やし**では通らない。
  旧ラベル（drill/apply/think）は手数基準なので **[NG]**＝新定義で付け直す。
  考え方の全文：`holiday/reports/2026-08-20_難易度の測り方を手数から認知過程へ_設計.md`
- `check_coverage.py` は**各ページの visual_emphasis が空ならNG**（＝pages_scanned に名前を
  並べただけの「読んでいない範囲」を通さない。②全範囲読了の機械的担保）。**生成前に必ず通す。**
- 配布 `publish_to_drive.sh` は内部で `run_checks.sh` を先に通す（出題履歴JSONを渡す）ので、
  ①漏れ④つまずきが揃わないと**そもそもDriveへ上げられない**。②は上の生成前カバレッジで担保。
- `check_leak.py` は **見出し(h2)への漏れがあれば終了コード非ゼロ＝停止**。
  **設問文への語句一致は「注意（⚠）」表示**で止めない（同じ語が選択肢・文脈で頻出し、
  一律ブロックすると誤検知が多いため）。**⚠は1件ずつ目視し、本当に別の設問の答えを
  割っていないか確認する**（例：ある設問の答えの固有語が別の設問文にそのまま出ていないか）。
  頻出の一般語（気候帯名など）や二択の選択肢は許容、固有語の重複は言い換えて消す。
- **見出しには出題範囲の単元名だけ**を書く（答えを書かない）。

**② 配点・時間の検算（assert）** を流す（ステップ5.5。テスト固有のため各自でPython）。

**③ answer-validator を必ず通す（省略禁止・コードでは強制できないので手順で担保）。**
生成の最後に必ず answer-validator スキルへHTMLを渡し、解き直し・転記突合・知識検証まで出す。
**指摘される前に自分から通すこと**（2026-08-09 専務叱責）。

**④ 体裁を目で見る。**
書き出したHTMLをブラウザで開き、**巻末の解答・解説まで通して**崩れていないことを確認する。
印刷が必要なときはブラウザの「印刷 → PDFに保存」を使う。A4用のCSSはテンプレートに入っている。

### 承認の自己チェックリスト（★2026-08-18 から機械の関門で強制する）
**質問・承認ターンを飛ばすのは専務の再三の指摘事項**（「skillどおりに質問確認ターンを実施しない」）。
honor system をやめ、**`check_approvals.py` が出題履歴JSONの `approvals` を見て配信を止める**。
黙って先へ進んでも、最後の `publish_to_drive.sh` で必ず落ちる。記録の書き方はステップ8を参照。
各承認ターンでは次を宣言してから待つ：
- [ ] ステップ4：コア項目リストを提示し、**承認を得るまでテスト構成へ進まない**
- [ ] ステップ5：テスト構成（大問・配点）を提示し、**承認を得るまでHTML生成へ進まない**
- [ ] ステップ5.6：難易度の構成比（load の内訳）を提示し、**承認を得るまでHTML生成へ進まない**
- [ ] 生成後：①ランナー ②配点検算 ③answer-validator ④配布の関門（publish_to_drive.sh＝PDF化＋3点アップ＋着地検証）を**この順で全て通してから**URLを提示

## ステップ 8：出題履歴 JSON の出力

HTML生成後に、次回テスト作成に使用する出題履歴JSONを生成する。
HTMLと同じフォルダに出力する（`json.dump(..., ensure_ascii=False, indent=2)`）。

### 出題履歴JSONの形式

```json
{
  "created_at": "YYYY-MM-DD",
  "subject": "教科名",
  "unit": "単元名",
  "level": "基礎 / 標準 / 応用",
  "difficulty_primary": "complexity / process",
  "description_volume": "多め / 標準 / 少なめ",
  "total_points": 100,
  "time_limit": 50,
  "questions": [
    {
      "mondai_id": "大問1-(1)",
      "core_item": "コア項目名",
      "format": "選択 / 穴埋め / 記述 / 表 / 図表読み取り など",
      "difficulty": 0,
      "load": "recall / select / construct",
      "complexity": "low / mid / high",
      "point": 2,
      "pitfall": "狙うつまずき（常設カタログ記号＋単元固有）。無ければ \"なし（知識確認）\""
    }
  ]
}
```

※ `difficulty_primary`（2026-08-20 2軸化）＝難易度の**主軸**を宣言する。
　 **"complexity"**（数学・理科計算・英語＝計算/複合が作れる）／**"process"**（漢字・社会用語・国語文法＝暗記が原子的）。
　 未宣言なら process（従来挙動）＋[注意]。`check_difficulty.py` がこの値で判定軸を切り替える。
※ `complexity`（low/mid/high）＝**内容の要素相互作用性**。**difficulty_primary=complexity の教科は全設問に必須**。
　 process 教科でも付けてよい（判定は load を使う）。

※ `total_points`・各設問の `point` は**必須**（2026-08-18）。配信前の `run_checks.sh` の配点検算が
　 **`questions[].point` の合計 == `total_points`** を機械で照合する（合わなければ配信不可）。
　 満点は `TOTAL_POINTS`（ステップ3）と一致させる。**この欄が無いと配点検算が発火せず素通りする**
　 （旧版は `daimon_summary` を判定キーにしていたが、スキルが出力せず全模試が skip していた＝
　 承認関門・配点検算がともに無効化。判定を `questions` に統一し、配点は `point` から取るよう修正）。
　 `time_limit` は `TIME_LIMIT` と一致させる。
※ `pitfall` は**全コア項目に必須**（2026-08-11）。ステップ2④の「つまずきを重ねて出題」を
　 機械で担保する `check_pitfalls.py` がこの欄を見る。**キーごと省くのは不可**＝罠が無い問は
　 `"なし（知識確認）"` と明示する。罠を狙う問は**巻末（解説）に「▶よくある誤り」を1行**書くこと。
※ `load`（recall/select/construct）は**全設問に必須**、`complexity`（low/mid/high）は
　 **difficulty_primary=complexity の教科で全設問に必須**（2026-08-19 新設／2026-08-20 定義改訂・2軸化）。
　 配信前の `run_checks.sh` の **`check_difficulty.py`** が `difficulty_primary` で主軸を切り替え、
　 level（基本/標準/応用）に対する**主軸の設問数構成比**を照合する（1問=1票）。
　 complexity 教科の応用＝low≤30%・high≥30%・mid+high≥70%（**recall 上限なし**）／
　 process 教科の応用＝recall≤30%・construct≥15%・select+construct≥70%。**必須欄が無いと配信不可。**
　 `load` も `complexity` も format でも**手数でもない**＝「頭の中で何が起きるか・要素をいくつ関係づけるか」で決める。
　 旧ラベル（drill/apply/think＝手数基準）は [NG]。

### ★巻末の書式は av_report が機械で突合する（2026-08-19・省略禁止）

答えの検証（av_report）は**文字列の完全一致**で突合するため、次の3点を必ず守る。
外すと `完全性 NG`／`巻末①に無い出題` が全問に出て、HTMLを作り直す手戻りになる。

| 場所 | 正しい書き方 | やってはいけない |
|---|---|---|
| 出題履歴JSON | `"mondai_id": "大問1(1)"` | 巻末①と違う表記（`大問1-(1)` など） |
| 巻末①（`.ansrow`） | `<b>大問1(1)：</b> 猿人` | ラベルに配点を足す（`大問1(1)（2点）：`） |
| 巻末②（`.expttl`） | `大問1(1)　答え：猿人` | コア項目名だけを書く（答えが無いと 2B が空回りする） |

- **巻末①の答えは「答えそのもの」だけ**にする。「（〜も可）」などの許容表記を入れると
  2A の機械突合で不一致になる＝**許容は巻末②の解説に書く**（2026-08-19 に大問1(2)で発生）。

### 承認ターンの記録（模試は必須・2026-08-18）
`check_approvals.py` が見る欄。**無ければ配信できない**（run_checks.sh 経由でハード停止）。
```json
  "approvals": {
    "step3_settings": { "asked_at": "YYYY-MM-DD",
      "answers": {"満点": 40, "時間": 20, "記述量": "標準", "難易度": "標準", "配合": "バランス"} },
    "step4_core_items": { "presented_at": "YYYY-MM-DD", "approved": true },
    "step5_structure":  { "presented_at": "YYYY-MM-DD", "approved": true },
    "step5b_difficulty": { "presented_at": "YYYY-MM-DD", "approved": true,
      "mix": {"recall": 3, "select": 21, "construct": 7, "設問数": 31} }
  }
```
**専務が実際に答え・承認したことだけを書く。**先回りして true を書くのは、関門を自分で壊すのと同じ。

### 設計ブリーフの反映（本番の分析を引き継ぐ模試のみ・2026-08-13／作り方と意味はステップ2⑤）
過去の本番テストを分析して作った**教科ごとの設計ブリーフ**（例 `holiday/期末模試_設計ブリーフ/{教科}.md`）がある教科の模試は、
その方針を反映して作り、**出題履歴JSONに次の2つを必ず入れる**（＝反映したことの機械的な宣言）：
```json
  "design_brief_required": true,
  "design_brief_sha256": "<ブリーフの sha256（sha256sum で取得）>"
```
配信時は `DESIGN_BRIEF=<ブリーフのパス>` を付けて publish する（ステップ9）。
`check_calibration.py` が sha256 の一致を照合し、**未反映・不一致なら配信を拒否**する
（記憶に頼って方針を保持→飛ばす、を封じる恒久ゲート。ブリーフが無い教科・類題集・業務成果物は素通り）。

### 出力後の案内

JSONファイル出力後、チャットに以下を表示する。

```
【出題履歴JSONを出力しました】
次回テストを作成する際にこのJSONを渡すと、
今回と重複しない形式・切り口で問題を生成します。
```

## ステップ 9：出力と確認

- HTMLと出題履歴JSONを一時フォルダに書き出し、**ブラウザで体裁を確認してから**提示する
- **配信の前に answer-validator を通し、✗0件になったら `av_report.py`（検証レシート）→ `av_stamp.py`（合格スタンプ）の順で発行する**（2026-08-13 恒久ゲート／2026-08-17 レシート追加）。**av_stamp は `<html>.avcheck.json`（2A/2B/完全性の証拠物・sha一致・全問列挙・all_pass）が無いとスタンプを拒否**し、**publish は sha256一致の合格スタンプが無いと配信を拒否する**＝answer-validator を飛ばす（証拠を残さず「検証した」と言う）・検証後にHTMLを直す、が物理的にできない。
- 確認後、**配布の関門スクリプトでDriveへ上げる（PDF化＋HTML/PDF/出題履歴JSON の3点アップ＋着地検証。省略禁止）**：
  ```bash
  bash ~/.claude/skills/quiz-generator/references/publish_to_drive.sh <出力HTML> "<Drive教材フォルダ>" <出題履歴JSON>
  ```
  - **設計ブリーフのある教科の模試**（`design_brief_required:true`）は、必ず `DESIGN_BRIEF` を付ける：
    ```bash
    DESIGN_BRIEF=<設計ブリーフ.md のパス> bash ~/.claude/skills/quiz-generator/references/publish_to_drive.sh <出力HTML> "<Drive教材フォルダ>" <出題履歴JSON>
    ```
    付け忘れ／sha256不一致なら `check_calibration.py` が配信を拒否する（exit 7）。
  - 中でPDFを自動生成し、HTML＋PDF＋出題履歴JSON を `rclone copy` → **Drive側に3点が着地したか検証**する。
  - **ブラウザが無い等でPDFを作れなければ非ゼロで止まる**＝HTMLだけ上げてPDFが欠ける漏れを防ぐ（2026-08-10 数学の類似問題集で実際に発生した漏れの再発防止）。
  - 再生成でDriveを上書きするときも**必ずこのスクリプトを通す**（PDFも作り直し、古い版を残さない）。
- 修正依頼があれば大問単位で対応する

## ステップ 9.5：answer-validator からの修正依頼への対応

### トリガー
- 「answer-validator 検証結果」を含むテキストが渡された場合
- 「✗の問題を修正して」「検証結果に基づいて修正して」などの言及がある場合

### 処理手順

**① 修正内容の確認**
渡された検証結果から ✗ の問題を全件抽出し、以下を確認する。

| 確認項目 | 内容 |
|---------|------|
| 問題番号 | どの大問・小問が対象か |
| 修正種別 | 解き直し不一致 / 転記ミス のどちらか |
| 修正案 | answer-validator が提示した修正内容 |

**② 修正の適用**

- **解き直し不一致（答えが間違い）**：問題文・答え・解説を修正案に基づいて修正する
- **転記ミス（巻末①②の不一致）**：巻末①を正として巻末②を修正する

**③ HTML の再生成**

修正を適用してHTMLを再生成し、同じ場所に上書き保存する。
ファイル名は元のファイル名を維持する（`_fixed` などのサフィックスは付けない）。
**Driveへコピー済みの場合は、そちらも上書きする**（古い版が残らないようにする）。
出題履歴JSONは変更しない（答えの修正は出題履歴に影響しないため）。

**④ 再検証の案内**

```
修正済みHTMLを出力しました。
answer-validator で再検証することを推奨します。
```

## wrong_count の運用ルール

- JSONにエントリが存在する = 間違えたことがある問題
- JSONにエントリが存在しない = 間違えた記録がない問題
- wrong_count は quiz-generator が初回生成時に 1 で作成し、再生成のたびに +1 する
- mock-test-generator はこの値を読み取るだけで書き込まない
